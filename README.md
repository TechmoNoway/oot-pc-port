# OOT PC Port

An independent project exploring a native Windows x86-64 port of Ocarina of Time for Switch 2.

## Status

Early development. The Windows host builds and passes its native self-tests. The separate [experimental startup bootstrap](docs/startup-bootstrap.md) and [SDK runtime foundation](docs/sdk-runtime.md) compile selected original instructions into a private Windows executable, execute them only with explicit opt-in, and record precise stop diagnostics. The separate host-linked initialization experiment now reaches the original `nnMain` transition and stops before its body. The game is not playable yet.

The [initialization milestone](docs/sdk-initialization.md) adds owned native SDK providers, the required heap/protection effects and a bounded SIMD/scalar FP subset. Its [acceleration extension](docs/startup-acceleration.md) provides stable split generated C, incremental native builds, verified whole-function execution and separate offline-linked boot. Both MSVC and GCC complete all three original module constructor bodies exactly once, observe all seven required stages and reach the checked entry transition. Each run retires 1,521,646 original instructions plus 51 host scaffold instructions, with 15 native calls. Accelerated and single-step ordered trace digests agree on both compilers. The final `build/milestones/sdk-initialization-v1/` run passes all 36 stages: 573 Python tests without skips, seven CTest groups, 283,401 common native/reference comparisons per compiler, fresh unchanged survey outcomes and the source-fingerprint check. Earlier raw/SDK/logging endpoints and trace digests remain unchanged.

The input pipeline provides [metadata inspection](docs/input-inspection.md), verified [LZ4/ZBIC segment preparation](docs/segment-preparation.md), complete [offline linking](docs/offline-linking.md) and data-only [native image mapping](docs/runtime-images.md) with guarded synthetic stacks.

The [ARM64 C lifter](docs/arm64-lifter.md) supports selected integer/control-flow semantics, scalar/paired memory, [RCpc loads](docs/ordered-loads.md), [conditional comparisons](docs/conditional-compare.md), [widening](docs/long-multiply.md) and [high multiplication](docs/high-multiply.md), and [bit operations](docs/bit-operations.md). The preceding [integer-frontier milestone](docs/integer-frontier.md) adds EXTR/immediate ROR and all CRC32/CRC32C B/H/W/X variants. Unsupported encodings remain explicit failures.

[Checked guest memory](docs/guest-memory.md), [hash-bound registries](docs/bound-dispatch.md), [verified leaves](docs/leaf-verification.md), [stack/CFG dispatch](docs/stack-cfg.md), [fixed layouts](docs/stack-layouts.md), [PAC-aware frames](docs/pauth-stack-dispatch.md), [checked reads](docs/checked-reads.md), [LR-pair frames](docs/lr-pair-frames.md), [checked PLT bridges](docs/plt-dispatch.md), [checked memory effects](docs/checked-memory.md), [memory-leaf callees](docs/memory-callees.md) and [bounded loops/writeback](docs/bounded-memory.md) provide explicit register, memory, call, frame-ownership and resumable-budget contracts. PAC uses a separate [QARMA5/VA39 model](docs/pointer-authentication.md).

Synthetic translations and complete call graphs run natively on MSVC/GCC and are compared with pinned ARM64 reference execution and independent arithmetic/polynomial results. Static [analysis](docs/arm64-analysis.md), [profile surveys](docs/function-profile-survey.md) and [callee audits](docs/callee-audit.md) operate on original bytes without generating or executing game callbacks. Their candidate counts describe structural proofs and runtime obligations, not original function identity or gameplay coverage. The separate startup experiment has its own selected-code, memory, process-model and execution boundary.

The preceding raw startup work uses fresh raw 4 KiB page mappings because the original loader performs relocation itself; an independently linked copy supplies audit evidence. It supplies the verified NPDM stack size, private zeroed TLS, an initially unmapped reserved heap, checked QueryMemory/heap/debug/counter services and a one-shot pristine-image claim. Its NSO register/handle model is explicitly experimental and does not prove the Switch 2 ABI. Unsupported encodings, targets and services stop without invented successful results. Final validation passes 379 Python tests, seven CTest groups and 283,401 common native/reference cases per compiler. Startup tests add 480 complete runs/4,624 prefixes per compiler, 36 cross-module/chunk cases and 273 context checks.

The preceding startup bootstrap executes 40,397,142 original instructions on both MSVC and GCC, reaches SDK initialization and stops before unsupported GetInfo ID 11 (handle zero, sub-ID two). All eight audited entry-module relative-pointer probes match the independent linker, and full ordered trace SHA-256 values agree. Fresh audits, unchanged preceding profiles and the final source fingerprint also pass in `build/milestones/startup-bootstrap-v1/`.

The SDK extension supplies private entropy, verified-NPDM process declarations, read-only main-thread queries, explicit empty remote/extra-alias metadata, the owned allocation granule, TLS register operations and serialized scalar CAS32/64. It recognizes the original SDK lock-identity profile before initializing its observed TLS field; original code creates SDK thread objects. Its checked goal requires ordered stage-entry observations and the original `nnMain` branch transition. That foundation stopped at service-manager IPC. The newer initialization profile handles its admitted SDK families on the host and supplies the larger application heap; unsupported service objects and consumers remain explicit boundaries.

The final SDK foundation validation passes 415 Python tests, seven CTest groups and 283,401 common native/reference comparisons per compiler. SDK tests add 12,288 thread-register and 6,144 CAS state/memory reference cases, 80,000 concurrent CAS increments and 262,144 decoder combinations per compiler; the context self-test passes 7,810 checks on each compiler. Fresh audits preserve all preceding profile outcomes and reproduce the old startup trace exactly.

Both compilers now retire 40,399,581 original instructions, observe five of seven mandatory stage entries and stop at the real `ConnectToNamedPort` request for `sm:`. Their complete ordered trace digests agree and all eight relocation probes match. The OS and first libc initialization paths have returned; SDK module initialization has begun. The final `build/milestones/sdk-runtime-v1/` run passes every stage with a matching source fingerprint. SDK initialization, application entry and gameplay remain incomplete.

The preceding [hybrid native SDK profile](docs/native-sdk.md) keeps the checked translator and implements a coherent logging family directly on the host: initialization, destination, default-observer enablement and formatted-record emission. Thirteen original-export/body-bound entries cover four native operations and nine unsupported guards. The host owns logging state and bounded copies; it creates no fabricated SDK logger objects or successful IPC responses. Native calls have a separate trace event/count, preserve their declared ABI and cannot cover original initialization-goal markers.

Its final validation passes 444 Python tests, seven CTest groups, unchanged earlier surveys and six real startup experiments across MSVC/GCC. Both compilers reproduce the raw and original-SDK trace digests exactly. The hybrid run retires 40,400,024 original instructions plus one native logging initialization, matches all eight relocation probes and the complete ordered trace digest, and observes actual original OE initializer entry. It stops at the next `sm:` connection in the original platform path. Every stage and the source fingerprint pass in `build/milestones/native-sdk-v1/`. That logging-only profile remains a diagnostic; the newer initialization profile adds the owned platform family and required startup consumers.

The completed bounded-memory milestone adds leaf policy 3 and stack policy 10/schema 11: scalar/pair pre/post-index writeback and one verified counter-loop shape through direct and exact-PLT memory callees. A loop's first header admits only positive, decrement-divisible counts of at most 1,024 iterations. Full counter/control checks and a retirement ceiling survive yields; image grants, complete stack exclusion and live GOT protection remain enforced. Earlier policies retain their permissions.

The preceding bounded-memory validation passes 357 Python tests without skips, six CTest groups and 283,401 common native/reference comparisons per compiler. MSVC/GCC each validate 865 new whole calls/17,145 prefixes and 128 actual schema-11 factory calls/6,496 prefixes. Its surveys, audit, baseline comparisons and source fingerprint pass; private evidence is under `build/milestones/bounded-memory-v1/`.

The fresh original-byte 1.1.1 survey preserves all 16,805 preceding memory-leaf candidates and finds 554 additional regions: 251 acyclic writeback helpers and 303 bounded loops. Framed acceptance rises from 2,858 to 2,868 roots; newly closed roots use 12 distinct new helpers and 20 unique call edges. Five used helpers contain bounded loops, reached by two upgraded roots; the other seven are acyclic writeback helpers. These are static proofs with count, memory and GOT obligations. The game is not playable yet.

## Milestone delivery

Work proceeds through complete capability milestones. Each authorized milestone includes implementation, verifier/runtime integration, MSVC/GCC checks, fresh hash-matched surveys/audit, status documentation and a reviewed commit/push on `dev`. The assistant handles the dependent substeps without requiring another prompt for each instruction family.

The [milestone runner](docs/development-workflow.md) executes the complete evidence pipeline from one command, records stage checkpoints/logs and writes a private aggregate summary. Source changes, failed/skipped required checks, stale evidence or mismatched baselines prevent a successful final status. See [the current milestone configuration](config/milestones/sdk-initialization.json).

The hybrid direction prioritizes native implementations of coherent SDK families while retaining original game translation and necessary low-level services. The remaining platform, applet, account and filesystem consumers require real owned behavior; unimplemented paths remain explicit boundaries. The initialization experiment now accounts for the application heap and reaches the checked `nnMain` transition. Running its body, filesystem mounts, graphics/shaders and other host systems remain further work. See [architecture](docs/architecture.md) and [development workflow](docs/development-workflow.md).

Game containers, keys, extracted files, generated game code, saves, shader caches, compiled executables and detailed reports stay outside version control. Build output belongs under `build/`; future generated output belongs under `generated/`.
